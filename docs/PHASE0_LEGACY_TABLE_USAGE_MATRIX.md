# Phase 0 legacy-table source and usage matrix

**Review date:** 2026-11-22<br>
**Scope:** repository source only; no production database query or row access in this review.<br>
**Purpose:** map the 12 application tables observed in the earlier Plesk/phpMyAdmin inventory to current SSR, archived SQL backend, and legacy Firebase source references. This is not a live-runtime, backup, data-lineage, or deletion assessment.

## Evidence boundary

The prior production inventory recorded these 12 tables as present but not created by the current Laravel SSR migrations. This pass searched first-party source outside dependencies (`ssr/vendor`, `node_modules`, and `lib`). It found a tracked archived Flask/SQLAlchemy app at `legacy-archive/app.py` that configures the `erphpro` database using environment-provided credentials and maps nine of the observed table names. Its folder name and source code do not prove whether the app is running anywhere. The Laravel deployment's observed document root was `ssr/public`, but that does not establish that no separate process, old endpoint, or external integration uses the archived app/database.

Firebase collections are a separate storage namespace from MariaDB tables. Similar names are evidence of parallel source-code paths only; they do not prove shared records, synchronization, identity, completeness, or current traffic. The three `legacy_*` table names below have no exact first-party source-name match in this scan. Do not drop, truncate, rename, migrate, or seed over any of the 12 tables based on this matrix.

## Required evidence before closing the data-retention gate

### Archived Flask route side effects and reachability

Static inspection of `legacy-archive/app.py` found route-level SQL reads/writes for `articles`, `tasks`, `dskp_standards`, `leave_records`, and `system_settings`. The `calendar_events`, `notifications`, `reference_items`, and `timetable_templates` classes are mapped but no route-level ORM call site was found in that file. The three `legacy_*` tables have no exact first-party table-name match. These are source facts only; the archived app's deployment, route reachability, database identity, and any reverse-proxy access controls remain unverified.

The archived app contains no Flask `before_request` hook or route `login_required` decorator in the inspected source. Do not infer internet reachability from this: a separate proxy or host control may exist but was not inspected. If the app is reachable, its route side effects require immediate containment review before any production database write or cleanup. In particular, `POST /api/dskp/sync` defaults to replacement for a raw-list request or when `mode` is omitted, and calls a delete-all query before inserting the supplied rows. The route `/api/dskp/<int:id>` also permits item PUT/DELETE in source. No endpoint was called.

`GET /api/seed_2026` reads and executes `legacy-archive/seed_rph_2026.sql` when the file exists. A local metadata-only SQL scan found 395 `INSERT INTO lesson_plans` statements with one shared column signature (`id`, `school_id`, `teacher_id`, `teacher_name`, `subject`, `grade`, `class_name`, `time`, `topic`, `date`, `status`, `objectives`, `success_criteria`, `activities`, `updated_at`, `version`) and no other target table; SQL row values were not inspected, and the route/file were not executed. This signature is incompatible with the current SSR migration definition for `lesson_plans`, which requires `teacher_profile_id`, `lesson_date`, and `current_version` and has no `teacher_id`, `teacher_name`, `time`, `topic`, or `objectives` columns. This proves the archived seed is not compatible with the repository's current migration schema; it does not establish the exact live production table structure or what happens if the route is called there. Treat it as a potentially destructive and/or failing write surface requiring a reachability/configuration decision, not evidence that the seed was ever executed. The initial archive configuration defaults `DB_NAME` to `erphpro` and requires an externally supplied `DB_PASS`; this does not prove any production credentials are present.

Before classifying archive code or these tables as unused, obtain a read-only Plesk/application/process/task inventory and confirm the configured database target and proxy route. If the archived service is active or reachable, disable its write surface only through an approved, reviewed change with a recovery plan; do not test its mutating routes against production.

1. Establish whether the archived Flask application or another consumer is running, including Plesk applications, processes, scheduled jobs, API callers, and provider-side integrations; source-code presence alone cannot answer this.
2. In an authorized isolated restore, inventory table definitions, indexes, foreign keys, row counts, and representative schema-only metadata for all 12 tables. Do not expose or copy personal rows or configuration secrets into this report.
3. Verify that the restore covers these exact tables and passes an application-independent integrity check before treating any backup as a recovery point.
4. For any proposed migration, identify owner/source/version/rights, map keys and field semantics, compare source and target in isolation, and retain a reversible archive/export with counts and checksums.
5. Only after runtime consumers, ownership, retention obligations, and restore evidence are resolved may a separate scoped change propose archival or cleanup. This matrix grants no production-write authorization.

## Separate repository-local Python/SQLite schema

The repository also contains `backend/models.py`, a different Flask schema with tables `profiles`, `dskp_data`, `timetable`, `weekly_submissions`, and `lesson_entries`; none of those names matches the 12-table production inventory. `backend/config.py` defaults to `sqlite:///erph.db`, which Flask-SQLAlchemy resolves under `backend/instance/`; an explicitly supplied `DATABASE_URL` can select another backend. `backend/app.py` calls `db.create_all()` when creating its app and starts the development server with debug enabled when run directly. There is no source evidence in this checkout that this app is the active Plesk runtime.

Read-only local file metadata showed the tracked `backend/instance/erph.db` SQLite file contains five rows in `dskp_data` and zero rows in each of the four other model tables. No row values were read or copied. The file remains untouched and tracked; these five rows are not evidence of production DSKP coverage or an authorized curriculum source. The separate tracked `backend/erph.db` file was zero bytes, had no SQLite schema, and was not the configured default database path; it is removed in the local candidate as an unused empty artifact.

The prior `backend/seed_dskp.py` implementation deleted every `dskp_data` row and accepted the configured database URL. The local candidate now requires an explicit `--init-empty-local-demo` flag, refuses any explicit `DATABASE_URL`, refuses an existing non-empty local SQLite file or non-empty DSKP table, and performs no delete. Five standard-library regression tests run the copied script against temporary files and stubbed app/model modules; they cover the required flag, remote-URL refusal, preserving a non-empty file, refusing a populated DSKP table, and the explicit empty-demo path. `python3 -m unittest discover -s backend/tests -v` passes all five tests. The tracked SQLite file's SHA-256 remains unchanged. This harness does not exercise Flask-SQLAlchemy or the real stored rows; the actual seed path was not run because the local environment lacks Flask and, more importantly, the current database is non-empty. No local or production database rows were modified.

This separate SQLite data/source path is another reason not to merge `dskp_data`, MariaDB `dskp_standards`, Firebase `dskp_standards`, hierarchical Firestore curriculum, or SSR `curriculum_items` by name alone. Any future curriculum consolidation requires provenance, rights, version/language/grade mapping, duplicate/difference reporting, and isolated restore/import evidence.

### Minimum target-model questions before Phase 3 curriculum implementation

- Decide whether curriculum sources are platform-global, school licensed/imported, or both; define tenant isolation without duplicating national data unnecessarily.
- Define immutable source/version identifiers, curriculum framework/edition, source URL/document ID, rights/license and review status, language, school system/type, grade level, subject taxonomy, effective dates, and content checksum.
- Preserve SK and SP codes as structured fields, keep source text and normalized/search text separately, and define how `tema_bidang`, `tema`, skill/topic, and title are represented without loss.
- Define update/import semantics (append a new version, supersede, or withdraw) and audit identity; never overwrite a previously referenced RPH curriculum snapshot.
- Specify indexes from actual query shapes (framework/version + school type + grade + subject + SK/SP code), and compare MariaDB 10.5 behavior/performance on an isolated representative copy before production migration.
- Require per-source rights/provenance acceptance and a field-level mapping/difference report before data import. Existing RPHs must retain an immutable curriculum snapshot or version reference so later DSKP updates do not rewrite historical lesson plans.

These are Phase 0/architecture constraints for a later authorized curriculum phase. No target migration or importer was added in this pass because the production source lineage, rights, and version coverage are still unverified.
