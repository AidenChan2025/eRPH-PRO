## 2. 对 eRPH Pro 的产品启示

学生事务不应只是一个“学生名单”页面，而应成为学校的受控记录系统：

1. 学校管理员建立学生与班级基础档案。
2. 教师可以提交需要跟进的出勤、纪律或关怀事项。
3. 管理层可以分派、调查、采取措施并关闭案件。
4. 系统自动计算出勤率，并提供低于学校设定阈值的名单。
5. 校长、PK HEM 与获授权人员可以按状态、班级、年级和时间范围查看报告。
6. 每一项敏感操作都要记录操作者、时间、原因和前后变化。

## 3. 建议的未来模块边界

### 3.1 学生核心档案

- 学号/学校内部编号
- 姓名、身份证或出生登记资料（按学校政策决定是否保存）
- 性别、出生日期、年级、班级、组别
- 入学、转班、转校、毕业和离校状态
- 语言、宗教或其他学校确实需要的教育资料
- 紧急联系人与监护人关系
- 学生档案附件及有效期

核心原则：学生是学校租户内的档案，不把学生身份直接绑定某一位教师；教师离校或换班时，历史记录仍属于学校。

### 3.2 出勤与低出勤跟进

- 每日出勤、迟到、早退、缺席及缺席原因
- 按学校作息、上下午班和假期日历计算应到天数
- 自动计算 `出勤率 = 出席天数 / 应到天数 × 100%`
- 学校可配置预警阈值，默认建议使用 90%，但不得写死
- 低出勤名单、连续缺席、班级趋势和月份趋势
- 跟进记录：联络监护人、辅导、医疗证明、复查日期

出勤计算必须使用学校自己的学年、上课日和作息设定，不能假定所有学校星期和节数相同。

### 3.3 纪律案件

建议采用案件生命周期：

`报告 → 初步筛选 → 调查中 → 等待管理层决定 → 已采取措施 → 观察/跟进 → 已关闭`

每个案件至少包括：

- 案件编号、发生日期、地点和来源
- 涉及学生、报告教师、负责管理人员
- 事件类别、严重程度、事实描述
- 证据附件、证人或相关记录
- 学生陈述与监护人通知记录
- 管理决定、辅导/修复措施、处分记录
- 下次跟进日期、当前状态、关闭理由
- 全部变更的审计记录

系统应区分“事件报告”和“正式纪律案件”。教师提交的报告不应自动等同于已经确认的违规事实。

### 3.4 学生关怀与辅导

这是比普通学生档案更敏感的区域，未来应独立权限控制：

- 关怀转介
- 辅导预约与跟进
- 家庭或经济援助备注
- 学习适应或保护性关注
- 只显示给获授权人员的敏感摘要

普通教师不应默认看到完整辅导内容；系统应支持最小可见范围和字段级隐藏。

## 4. 建议的 SQL 扩展表

所有学校拥有的表必须带 `school_id`，并使用外键、索引、状态字段和审计关联。

| 表 | 用途 |
|---|---|
| `students` | 学生主档案与生命周期状态 |
| `student_guardians` | 学生与监护人的关系、联络方式、优先联系人 |
| `student_enrolments` | 入学、年级、班级、转班与离校历史 |
| `student_classes` | 学年内的班级与班主任关系 |
| `attendance_days` | 学校日历中的应到日与特殊日 |
| `student_attendance` | 学生每日出勤、迟到、早退与原因 |
| `discipline_cases` | 纪律案件主记录与生命周期 |
| `discipline_events` | 案件内的事件、调查、决定和跟进节点 |
| `discipline_actions` | 辅导、修复措施、处分及完成状态 |
| `student_welfare_cases` | 关怀/辅导案件，需更严格的权限 |
| `student_documents` | 证明、通知书、附件与保留期限 |
| `student_notifications` | 监护人通知、签收和联络记录 |

不要把所有未来字段塞进一个无限扩大的 `profile_data` JSON。学生主档案可以保留少量扩展 JSON，但出勤、案件、权限、报告所依赖的字段必须结构化，才能保证查询和审计可靠。

## 5. 权限设计预留

建议先预留权限名称，不在当前 RPH 版本启用：

- `student.records.view`
- `student.records.manage`
- `student.attendance.record`
- `student.attendance.view`
- `student.attendance.report`
- `discipline.report.create`
- `discipline.cases.view`
- `discipline.cases.manage`
- `discipline.cases.close`
- `student.welfare.view_sensitive`
- `student.documents.manage`
- `student.reports.export`

建议默认范围：教师只看自己授课/负责班级的必要资料；班主任看负责班级；PK HEM、校长和学校主管理员按学校政策查看全校；平台 Owner 只有在有明确援助理由、临时授权和审计记录时才进入学校资料。

## 6. Dashboard 与报告预留

未来学生事务 Dashboard 可以提供：

- 学生总数、活跃班级、近期转入/转出
- 今日缺席、迟到、连续缺席
- 出勤率低于学校阈值的学生数
- 未关闭纪律案件、按严重程度和状态分布
- 逾期未跟进案件
- 按年级、班级、月份的趋势
- 待管理层决定、待监护人通知、待关闭案件

所有数字必须带时间范围、学校范围和生成时间；导出报告要记录导出者、筛选条件和导出时间，避免把 Dashboard 数字误当成永久统计结果。

## 7. 隐私、安全与资料生命周期

学生事务比教案资料更敏感，未来实现必须先完成：

- 学校租户隔离和每个查询的 `school_id` 约束
- 细分角色与最小权限
- 敏感案件字段的额外访问控制
- 附件下载授权与下载审计
- 禁止用学生姓名、身份证号作为 URL 或公开导出文件名
- 资料更正、封存、保留期限和离校后的处理规则
- 导出前确认范围，默认不导出敏感辅导内容
- 监管/督学临时账号必须有到期时间、原因和完整日志
- 所有删除优先采用封存，不能静默删除正式纪律记录

## 8. 与当前开发阶段的关系

学生事务是未来模块，不进入当前 RPH MVP 的数据库迁移和菜单。当前只保留以下扩展接口：

1. 统一的学校租户与角色权限。
2. `audit_logs` 审计基础。
3. 学校设置、学年、作息和报告框架。
4. 未来模块可复用的学校成员与临时访问机制。
5. 未来模块 API/路由命名空间，例如 `/student-affairs`，但暂不开放功能。

下一阶段开发学生事务前，必须另行完成数据字典、权限矩阵、资料保留政策、案件流程确认和学校试点验收。

## 9. 建议开发顺序

1. 学生主档案、班级和入离校历史。
2. 出勤录入与可配置阈值报告。
3. 纪律报告与案件状态流转。
4. 管理层 Dashboard、导出和通知记录。
5. 关怀/辅导敏感模块。
6. 批量导入、Google Drive/文件导出和跨学校资料携带。

本模块暂不接入 Firebase；未来实现继续使用 Laravel SSR + SQL，前端只用 CSS 与渐进式 JavaScript 增强。
